Proof Pursuit — system architecture

Proof Pursuit — multi-agent system for verified mathematical research

AI-assisted mathematical research competition: 7 hours, 4 problems × 6 cells of increasing difficulty (1/2/3/5/8/13 points). Only verifiable proofs and certificates count. Nothing is sent to the platform from the repo: submissions remain drafts in problema-N/submission/ until a human approves them.

This README explains the entire pipeline: from the documents with the formalized problems, to the loop between the agents, to how and why each agent decides, up to the structured output (submissions + LaTeX report) to be uploaded to the platform.

Fixed points of the pipeline: - The statement is protected. The cell text enters state.json as cell_statement and the Referee judges that text: no agent can rephrase the target. - The literature is deterministic. literature.py queries arXiv (exact phrase, real ids, abstracts read) before the attempt; the Researcher must declare in literature_position whether it follows, adapts or departs from the state of the art and why. A result taken from a paper is CITED, not proven. - No agent ever declares “solved”. The Referee reaches at most READY_FOR_HUMAN; ACCEPT is a human signature.

It is this trace that ends up in the submission and in the LaTeX report (§6).

Why and when the Creative steps in

The Creative does not run at every iteration: it would cost and scatter effort. It steps in only when the cycle is spinning idly, and the loop recognizes this through three independent signals, each sufficient on its own (loop.py: serve_creative):

  1. the Researcher asks for it (request_creative: true): it believes it has exhausted the natural avenues;
  2. the Referee signals it (stagnation_signal): the same fatal error keeps repeating;
  3. the stagnation counter rises (state.stagnation_count): the Researcher itself detects, before attempting, that the latest attempts share the same family and the same reason for rejection (lexical similarity of the fatal_error).

When it steps in, it reads the whole history (not just the last attempt), writes why the block keeps repeating (blocker_analysis), what not to repeat (avoid) and genuinely different directions with declared risk (ideas). The Researcher of the next iteration sees these ideas in the prompt and must say which one it follows and why. The Creative certifies nothing and never declares a cell solved: that remains the job of the Referee, then of the human.

Why two judges and a model-free merge

A single model saying “correct” is not a proof. The Referee separates two questions that are readily confused: is it true? (A: logic, missing cases, target mismatch, upper bound passed off as exact value) and is it proven with what has been shown? (B: sources retrieved or not, computations reproduced or not, exhaustive or sampled, float or exact). Neither judge sees the other. The merge is deterministic code with consistency rules: a PASS with a fatal error is rejected by the validator; a judge that cannot judge returns a limitation, which is never a FAIL. If a judge attaches a reservation to a valid report, the bridge moves it into the notes instead of losing the judgment (this was the real case of U(Q₅): a well-motivated PASS discarded for one field too many). Similarly, if B classifies the already-verified claims too, the bridge keeps only the candidate’s ones, as the merge validator requires. The normalizations only remove, they never add. bridge_referee.py review --replay re-merges the last saved raw reports without calling the models again: useful after a fix to the bridge.

5. The contracts (shared/schemas)

  • state.schema.json — current_target, cell_statement (protected), verified_claims[], failed_attempts[], stagnation_count, cell_status with allowed states SOLVED · SOLVED_BY_COMPUTATION · PARTIAL_PROGRESS · UNRESOLVED · KNOWN_OPEN · FALSE. The Researcher touches only stagnation_count; highest_verified_cell is moved only by the Referee.
  • attempt.schema.json — all fields mandatory (literature_position included); claimed_status ∈ CELL_SOLVED_CANDIDATE · LEMMA_CANDIDATE · NUMERICAL_EVIDENCE_ONLY · LITERATURE_ONLY · COUNTEREXAMPLE_CANDIDATE · NO_PROGRESS.
  • referee_report.schema.json — verdict, review_status (READY_FOR_HUMAN ≠ ACCEPT), fatal_error, next_blocker, accepted_claims, stagnation_signal.
  • creative_ideas.schema.json — blocker_analysis, avoid[], ideas[] with risk and motivations.

6. Structured output for the platform

For each cell the platform receives a written submission. Here the path is:

  1. Loop STOP with READY_FOR_HUMAN ⇒ a human writes problema-N/submission/parte-K.md following CLAUDE.md: result and scope · complete proof (or certificate + justification) · verification instructions with measured times · sources (distinguishing existing results and our contribution) · limitations.
  2. Human critical review (missing hypotheses, circularity, code/statement discrepancies) ⇒ STATUS.md moves to revisionato. A READY_FOR_HUMAN verdict without review remains bozza pronta.
  3. LaTeX report tools/build_report.py ⇒ report/proof_pursuit.tex, for each problem and cell: official statement · status · submission (proof) · agents’ decisions iteration by iteration (family, reason, verdict, fatal error, Creative’s intervention and its analysis) · code the proof rests on, with the outcome of the trusted re-run and the Referee’s verdict · arXiv citations found by the deterministic search and used by the Researcher, with the declared position relative to the state of the art.

Golden rule (CLAUDE.md): PROVEN / CITED (with source) / VERIFIED ON A FINITE RANGE / CONJECTURE are four different things and the submission keeps them separate.

7. How to use it

python3 -m venv .venv && .venv/bin/pip install numpy mpmath pydantic     # ambiente
tools/run_tests.sh                                                        # tutte le suite, senza modelli
tools/cerca_letteratura.sh                                                # arXiv → problema-N/fonti/arxiv.json
.venv/bin/python tools/prepara_runs.py p1 p2                              # cartelle runs/pN_cK
tools/lancia_loop.sh p1 2                # loop reale su tutte le celle di P1, 2 iterazioni, in parallelo
tools/lancia_loop.sh p2 2 3 4 5 6        # P2, solo celle 3–6 (1–2 già chiuse)
.venv/bin/python researcher/loop.py --workdir runs/p1_c1 --max-iter 3 --researcher-backend cli --shell full \
      --referee cli --creative cli      # una cella sola, a mano
.venv/bin/python tools/build_report.py   # → report/proof_pursuit.tex (+ HTML di anteprima se c'è pandoc)

Operational notes: the Researcher with shell full runs with pre-authorized permissions and must be started from a human terminal (in Claude Code: ! prefix). Backend: claude -p --json-schema with a subscription; no API key needed. Testing the cycle without models: --researcher-backend mock --referee mock --creative rule_based.

8. Minimum rules for collaborating

  1. Branch per person/part, small PRs to main; STATUS.md is updated in the same PR.
  2. Clean code: small functions, comments in Italian saying what and why, no duplicated dependencies.
  3. Every experiment: reproducible command, seed, times. Every certificate: separate from the research.
  4. No submission to the platform from the repo.
